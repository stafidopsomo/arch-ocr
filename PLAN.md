# arch-ocr Plan

This is the working plan for rebuilding `arch-ocr` into a cloud-first packet
validation system for Greek property, architecture, and building/legal
documents.

## North Star

The product is not simply OCR.

The real workflow is:

```text
document packet
-> page-level evidence extraction
-> entity clustering
-> cross-check validation
-> structured result JSON
-> optional human report
```

Users may upload 30 to 40 related pages for the same client, office, address,
architect, engineer, owner, property, or legal/building case. The system should
read every page, extract important printed/handwritten/stamped/signed values,
preserve nearby text, group repeated values, flag variations, and produce a
validation result based only on page evidence.

The final report does not need to be generated by this app at first. The most
important deliverable is reliable structured JSON that can feed another AI
system, a UI, or a future report generator.

## Product Layers

The project should be built in two layers.

### Backend Processing Engine

This is the current focus.

Responsibilities:

- local page triage
- cloud extraction
- evidence JSON
- packet clustering
- validation checks
- cost tracking
- Railway worker/API later

The backend should not depend on a specific frontend.

### Web App Layer

This comes later.

Likely responsibilities:

- account login
- upload packet
- job status
- past reports/results database
- report viewer
- export JSON/report

The web app should keep past results and reports, but not necessarily original
input files forever. Uploaded source files can be deleted after processing or
after a short retention window to control storage cost and privacy risk.

## Current Baseline

Implemented:

- PDF page rendering to PNG via PyMuPDF.
- image input support.
- Gemini provider for cheap/free-tier vision LLM extraction.
- Google Vision provider for OCR baseline.
- OpenRouter provider for hosted model experiments.
- markdown report mode.
- `--json-mode` extraction mode.
- normalized `arch_ocr.extraction.v1` JSON artifacts.
- extraction artifacts include local page triage and source/page references.
- model JSON is schema-validated before it is accepted.
- raw provider JSON output for debugging.
- local packet/page triage command with no cloud API calls.
- private packet fixture convention under `test_inputs/private/`.

Removed from the active path:

- local Tesseract/EasyOCR/PaddleOCR/docTR experiments.
- local Ollama assumptions.
- stale FastAPI webapp.
- old multi-engine PDF report workflow.

## Setup

Create and activate the Python environment:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
cp .env.example .env
```

Recommended cheap provider:

```env
CLOUD_PROVIDER=gemini
GEMINI_API_KEY=your_key_here
GEMINI_MODEL=gemini-3.1-flash-lite-preview
```

One-page markdown test:

```bash
python ocr_script.py test_inputs/example_page1.pdf \
  --provider gemini \
  --max-pages 1 \
  --output output/example_page1_gemini.md \
  --raw-output output/example_page1_gemini_raw.json
```

One-page structured extraction test:

```bash
python ocr_script.py test_inputs/example_page1.pdf \
  --provider gemini \
  --json-mode \
  --max-pages 1 \
  --output output/example_page1_gemini_extraction.json \
  --raw-output output/example_page1_gemini_extraction_raw.json
```

Local page triage, no API calls:

```bash
python ocr_script.py triage test_inputs/private/packet_001 \
  --output output/packet_001_triage.json
```

Google Vision OCR baseline:

```env
CLOUD_PROVIDER=google-vision
GOOGLE_VISION_API_KEY=your_key_here
GOOGLE_VISION_LANGUAGE_HINTS=el,en
```

```bash
python ocr_script.py test_inputs/example_page1.pdf \
  --provider google-vision \
  --output output/example_page1_google_vision.md
```

Cost discipline:

- Start with `--max-pages 1`.
- Keep `--dpi` around `130` to `170` for scanned forms.
- Save `--raw-output` while comparing providers.
- Compare Gemini extraction against Google Vision OCR before scaling up.
- Avoid full 40-page packets until the schema and prompts are stable.

## Core Principle

Never jump straight from images to a final report.

Build an evidence layer first. Every conclusion must cite the evidence records
it came from.

## Processing Pipeline

### 1. Packet Intake

Input may be:

- one multi-page PDF.
- many PDFs.
- image files.
- a local folder.
- a future Railway web upload batch.

The system should create a packet record:

```json
{
  "packet_id": "uuid",
  "source_files": [],
  "created_at": "iso timestamp",
  "page_count": 0,
  "provider_config": {}
}
```

### 2. Page Rendering

Each PDF page is rendered to an image and receives a stable identity:

```json
{
  "page_id": "uuid-or-hash",
  "source_file": "document.pdf",
  "page_number": 7,
  "image_path": "runtime path or object key",
  "dpi": 150
}
```

Every extracted field must remain traceable back to a specific page.

### 3. Page Triage

Before deciding which provider path to use, every page should be classified.

Triage metadata:

```json
{
  "page_id": "page-7",
  "source_file": "document.pdf",
  "page_number": 7,
  "embedded_text_chars": 2860,
  "image_count": 1,
  "annotation_count": 0,
  "page_kind": "born_digital | scanned | mixed | unknown",
  "needs_vision": true,
  "needs_text_layer": true,
  "possible_handwriting_or_stamp": "yes | no | unknown"
}
```

Rules:

- If a page has meaningful embedded text and few/no full-page images, it is
  probably born-digital.
- If a page has no embedded text and one or more large page images, it is
  probably scanned.
- If a page has embedded text plus images/annotations/stamps/signatures, it is
  mixed and should still get a rendered visual pass.
- Static PDF inspection cannot perfectly prove that no handwriting exists. A
  born-digital PDF can still have handwriting, stamps, or signatures layered on
  top or baked into an image.

Cheap strategy:

1. Extract the native text layer when available.
2. Render a page image anyway for mixed/unknown pages.
3. Ask a cheap vision model to classify whether handwriting, stamps, or
   signatures are visible.
4. Only run full field extraction on pages that need it.

Current implementation covers the local part of this:

```bash
python ocr_script.py triage <pdf-image-or-folder>
```

It does not call Gemini or Google Vision. It inspects each page locally with
PyMuPDF and records text-layer length, image count, annotation count, ink ratio,
page kind, and whether the page probably needs vision.

Extraction artifacts also include the relevant page triage data so every model
result can be interpreted in context.

Schema validation happens before the extraction artifact is written. The model
response must include required keys such as `schema_version`, `page_results`,
`fields`, `field_type`, `value`, `confidence`, and basic evidence fields.
Invalid responses fail with explicit JSON paths instead of silently entering the
packet pipeline.

### 4. Page-Level Evidence Extraction

Each page is processed independently first. This keeps prompts focused, costs
controlled, and debugging sane.

Current target page schema:

```json
{
  "schema_version": "page_evidence.v1",
  "packet_summary": "short summary",
  "page_results": [
    {
      "page_number": 1,
      "document_type": "building permit | declaration | plan | contract | technical memo | uncertain | other",
      "language": "el | en | mixed | uncertain",
      "printed_text_summary": "short summary",
      "fields": [
        {
          "field_id": "p1-f1",
          "field_type": "person_name | address | office | property_id | date | permit_number | engineer | architect | owner | applicant | handwritten_note | stamp | signature | technical_value | other",
          "label_text": "printed or nearby words that label the value, or uncertain",
          "value": "detected value, or uncertain",
          "normalized_value": "clean normalized form if safe, else same as value or uncertain",
          "is_handwritten": false,
          "is_stamped": false,
          "is_signature": false,
          "confidence": "high | medium | low",
          "evidence": {
            "nearby_text": "words before/after or around the value",
            "location_hint": "top right | table row | signature area | margin | uncertain"
          },
          "notes": ["uncertainty, variation, or reading notes"]
        }
      ],
      "page_warnings": []
    }
  ],
  "uncertainties": []
}
```

Handwritten values are especially important. The system must record nearby
printed words before/after the handwritten value so we know whether a name was
an owner, applicant, architect, engineer, witness, or something else.

### 5. Optional OCR Baseline

Google Vision can run before or beside Gemini.

Use Google Vision for:

- raw Greek OCR text.
- printed labels around handwritten values.
- cheap quality/readability baseline.

Hybrid prompt idea:

```text
Here is the page image.
Here is baseline OCR text from Google Vision.
Use the image as the source of truth, but use OCR text to help read printed
labels and nearby context.
```

Hybrid mode should be optional. It should be used only when it measurably
improves extraction or lowers cost.

### 6. Entity Clustering

After all pages are extracted, group fields that appear to refer to the same
real-world thing.

Examples:

- same person name with spelling variations.
- same address with abbreviations or missing street number.
- same permit or registry number appearing on several pages.
- same architect/engineer referenced by printed text, stamp, and signature.

Cluster record:

```json
{
  "cluster_id": "name-1",
  "field_type": "person_name",
  "canonical_value": "Nikos Papadopoulos",
  "mentions": [
    {
      "field_id": "page-2:p2-f4",
      "value": "ΝΙΚΟΣ ΠΑΠΑΔΟΠΟΥΛΟΣ",
      "page_id": "page-2",
      "source_file": "document.pdf",
      "confidence": "high",
      "nearby_label": "Owner"
    }
  ],
  "variation_notes": []
}
```

Start simple with deterministic normalization and fuzzy string matching. Later,
use an LLM only for ambiguous merges.

### 7. Cross-Checks

The validation engine reads clusters and page evidence, then emits checks:

```json
{
  "check_id": "address-consistency",
  "status": "pass | warning | fail | unknown",
  "title": "Address consistency",
  "summary": "Address X appears 5 times, with 1 variation on page 14.",
  "evidence_refs": ["page-1:p1-f3", "page-14:p14-f8"],
  "details": []
}
```

Initial checks:

- client/person name consistency.
- address consistency.
- office/company consistency.
- architect/engineer identity.
- owner/applicant identity.
- permit/registry/property identifier consistency.
- date consistency.
- missing signatures.
- missing stamps.
- handwritten amendments.
- extra unexpected names.
- low-confidence or unreadable fields.

Example conclusion:

```text
Name A appears 10 times as owner/applicant with high confidence.
Address X appears 5 times, but page 14 contains a street-number variation.
Architect Y appears in printed text on pages 3 and 8 and as a stamp/signature
on page 22.
One additional name appears once on page 17 and needs review.
```

### 8. Final Packet Output

The final packet artifact should be machine-readable first:

```json
{
  "artifact_version": "arch_ocr.packet.v1",
  "packet_id": "uuid",
  "summary": {
    "overall_status": "pass | warning | fail | needs_review",
    "main_client": "string or uncertain",
    "main_address": "string or uncertain",
    "main_architect_or_engineer": "string or uncertain"
  },
  "source_files": [],
  "page_results": [],
  "clusters": [],
  "checks": [],
  "uncertainties": []
}
```

## Why Not Process 40 Pages In One Prompt?

One giant prompt is the wrong first design.

Problems:

- expensive.
- hard to debug.
- weak traceability.
- easy for the model to blur pages together.
- difficult to re-run only failed pages.
- harder to prove where a conclusion came from.

Better design:

- extract page by page.
- store evidence.
- cluster values.
- validate clusters.
- generate final conclusion.

### Milestone 2: Page Extraction Hardening - Mostly Done

Goal: make page-level JSON stable enough to trust as an internal contract.

Tasks:

- Done: add validation for required keys:
  - `schema_version`
  - `page_results`
  - `fields`
  - `field_id`
  - `field_type`
  - `value`
  - `confidence`
- Done: fail clearly when provider JSON is invalid.
- Done: add field count and low-confidence count to extraction artifacts.
- Done: add `source_file`, `page_number`, `page_id`, and `field_ref` to field
  evidence records.
- Done: add page triage metadata:
  - embedded text character count
  - image count
  - page kind
  - needs vision yes/no
- Later: move schema definitions into dedicated schema module/file if the code
  grows.
- Later: capture provider token usage into normalized extraction artifacts.

Success criteria:

- Done: each accepted page extraction is valid JSON.
- Done: invalid model JSON fails clearly.
- Done: every field can be traced to page and file.
- Done: each page has enough metadata to choose text-first, vision-first, or hybrid
  processing.

### Milestone 3: Packet CLI - Next

Goal: process many files/pages and emit a single packet artifact.

Proposed command:

```bash
python ocr_script.py packet test_inputs/private/packet_001 \
  --provider gemini \
  --max-pages-per-file 5 \
  --output output/packet_001.json
```

Tasks:

- Add subcommands or a new `packet` mode.
- Accept a folder of PDFs/images.
- Render/process pages one page or one file at a time.
- Save per-page extraction artifacts.
- Combine page results into `arch_ocr.packet.v1`.
- Add resumable output so failed pages can be retried.

Success criteria:

- a folder of documents produces one `packet.json`.
- failed pages are reported, not silently ignored.
- packet JSON includes all page evidence.

### Milestone 4: Normalization And Clustering

Goal: group repeated facts across pages.

Tasks:

- Normalize Greek/Latin whitespace and punctuation.
- Normalize uppercase/lowercase.
- Normalize dates.
- Normalize common address abbreviations.
- Group exact normalized matches first.
- Add fuzzy matching for near-duplicates.
- Keep all mentions even when clustered.

Success criteria:

- repeated names and addresses are counted.
- obvious variations are grouped or flagged.
- clusters retain evidence refs.

### Milestone 5: Validation Checks

Goal: produce useful conclusions from clusters.

Tasks:

- Add checks for names, addresses, offices, engineers/architects, dates,
  identifiers, signatures, stamps, and unexpected extras.
- Assign statuses:
  - `pass`
  - `warning`
  - `fail`
  - `unknown`
- Include evidence refs in every check.
- Produce a short summary from deterministic checks first.

Success criteria:

- packet output can say what repeats, what varies, and what needs review.
- no conclusion exists without evidence refs.

### Milestone 6: Cost Tracking

Goal: understand cost before selling this per client.

Tasks:

- Record per request:
  - provider
  - model
  - source file
  - page number
  - input tokens
  - output tokens
  - image tokens when reported
  - runtime
  - estimated cost
- Aggregate cost per packet.
- Add a dry-run estimator using page count and last known average token usage.
- Keep native-text pages cheaper by avoiding full vision extraction when safe.

Success criteria:

- packet output includes estimated cost.
- we can estimate how many pages a 50 EUR/month client can process.
- expensive pages are visible in logs.

### Milestone 7: Provider Comparison And Hybrid Mode

Goal: decide when Google Vision helps.

Tasks:

- Add a comparison command for one page.
- Run Gemini-only extraction.
- Run Google Vision OCR.
- Run Gemini-with-OCR-context extraction.
- Compare field counts, confidence, and visible errors.

Success criteria:

- we know whether hybrid mode is worth its cost on real documents.
- Google Vision remains optional.

### Milestone 8: Railway API

Goal: upload and process packets in the cloud.

Railway deployment shape:

- FastAPI backend.
- upload endpoint for packets.
- background job queue or simple worker.
- persistent storage for uploaded files/rendered pages.
- database tables for packets, pages, fields, clusters, checks.
- provider API keys as Railway environment variables.
- downloadable JSON result.

First Railway milestone:

- upload one PDF.
- render pages.
- process only first N pages.
- save JSON output.
- return job status.

Do not build the final user UI before the packet JSON contract is stable.

### Milestone 9: Review UI And Reporting

Goal: make validation easy to inspect.

UI should show:

- uploaded packet.
- page thumbnails or page IDs.
- extracted fields per page.
- clusters of repeated names/addresses/identifiers.
- warnings and contradictions.
- raw OCR/model output for debugging.
- export JSON.
- optional markdown/human report.

## Immediate Next Task

Start **Milestone 3: Packet CLI**.

Implement a folder-level packet command that uses the completed triage and
validated extraction pieces.

Proposed command:

```bash
python ocr_script.py packet test_inputs/private/packet_001 \
  --provider gemini \
  --max-pages-per-file 2 \
  --output output/packet_001.json
```

First packet implementation can be conservative:

1. Run local triage for all files/pages.
2. Process only the first `N` pages per file.
3. Save per-page extraction artifacts internally or inside the packet output.
4. Collect failures per page instead of stopping the whole packet.
5. Emit `arch_ocr.packet.v1` with:
   - packet metadata
   - triage
   - page extraction artifacts
   - initial totals
   - errors

Do not implement clustering in the first packet pass. Packet mode should first
prove that multi-file, multi-page extraction is reliable and resumable.
